# TRAE 账号安全管家 (trae-device-security)

## Skill 概述

本 Skill 是 TRAE 用户的多合一账号安全管理工具。它帮助你在多台设备间使用 TRAE 时追踪登录状态，当遇到风控限制时快速定位问题根因并给出可操作的诊断报告，同时支持根据你的问题描述智能生成结构化的论坛反馈帖（产品建议 / 求助），并通过 Playwright MCP 自动发布到 TRAE 社区。核心价值：**把分散的账号安全问题收敛到统一入口处理，减少反复沟通成本**。

## 模块 A：设备登录记录与追踪

### A.1 存储位置

所有设备日志持久化存储于：

```
~/.trae/device-log.json
```

若目录不存在则首次写入时自动创建。

### A.2 数据结构

```json
{
  "version": "1.0",
  "lastUpdated": "2026-05-12T10:30:00Z",
  "devices": [
    {
      "id": "dev_001",
      "hostname": "macbook-pro-m1",
      "os": "macOS 15.3",
      "ip": "192.168.1.100",
      "loginTime": "2026-05-01T09:00:00Z",
      "lastActive": "2026-05-12T08:15:00Z",
      "status": "active",
      "tags": ["home", "primary"]
    }
  ],
  "riskEvents": []
}
```

字段说明：

- `devices[].status` 取值：`active`（在线） / `inactive`（超过 7 天未活跃） / `revoked`（手动注销）
- `devices[].tags` 自由标记，推荐值：`home` `office` `public` `temporary`
- `riskEvents` 由模块 B 自动填充

### A.3 操作指引

#### 记录新设备登录

读取现有 `device-log.json`，追加一条 device 记录，更新 `lastUpdated` 时间戳。若文件不存在则创建初始结构。

为什么这样做？因为 TRAE 的设备管理界面可能不暴露完整历史，本地日志是你自己的证据链——当需要向客服申诉时，精确的登录时间线能大幅缩短排查时间。

#### 查询设备列表

按 `lastActive` 倒序排列输出，标注每台设备距当前的天数差。对 `inactive` 设备用 ⚠️ 标记，对 `public` / `temporary` 标签的设备用 🔴 高亮。

#### 清理过期设备

将 `status` 为 `inactive` 且 `lastActive` 超过 **30 天** 的设备标记为 `stale`，询问用户是否确认移除。`public` 标签设备无论活跃时间一律提示优先清理。

#### 导出报告

生成 Markdown 格式的设备清单，包含统计摘要（总设备数 / 活跃数 / 风险设备数）。

## 模块 B：风控预警与智能诊断

### B.1 风控识别关键词

系统通过以下关键词模式匹配用户描述中的风控信号：

| 关键词 | 匹配方式 | 严重等级 |
|--------|---------|---------|
| 今天先到这里也不错 | 精确 / 近似 | 🔴 严重 |
| 好好休息下(明天再继续) | 模糊匹配 | 🟡 警告 |
| 设备数量已达上限 | 精确匹配 | 🔴 严重 |
| 连接数超限 / too many devices | 中英模糊 | 🟡 警告 |
| 账号异常 / 安全验证 | 宽泛匹配 | 🟠 提醒 |
| 登录受限 / 暂时无法使用 | 宽泛匹配 | 🟠 提醒 |

### B.2 分级预警机制

```
🔴 严重 (CRITICAL)
├── 触发条件：命中"设备上限"类关键词 或 同一账号短时间跨 ≥3 个不同 IP 登录
├── 立即动作：
│   1. 生成完整诊断报告
│   2. 列出所有已知设备及最近活跃时间
│   3. 给出解封步骤（等待冷却 → 清理旧设备 → 重新登录）
│   4. 建议是否需要生成论坛求助帖
└── 输出格式：见 B.3 诊断报告模板

🟡 警告 (WARNING)
├── 触发条件：命中"休息/暂停"类关键词 或 检测到新环境首次登录
├── 立即动作：
│   1. 确认是否为正常换机行为
│   2. 提示当前活跃设备数量及风险设备
│   3. 建议主动清理非必要设备
└── 输出格式：精简版摘要 + 操作建议

🟠 提醒 (INFO)
├── 触发条件：宽泛匹配到安全相关词汇但无明确风控事件
├── 立即动作：
│   1. 展示当前设备健康度概览
│   2. 提供"深度扫描"选项
└── 输出格式：单行状态卡片
```

**格式示例参考**（以"账号设备管理功能"为例）：

【P0 - 最紧急】增加设备管理页面

## 模块 D：论坛自动化发帖（Playwright MCP）

### D.1 发帖前置条件

- Playwright MCP 服务已启动且可用
- 用户已提供 TRAE 论坛登录凭证（或当前会话已登录）
- 目标帖子内容已通过模块 C 生成完毕

### D.2 发帖步骤

```
Step 1: 打开论坛首页
  → 导航至 https://community.trae.ai （或实际论坛地址）

Step 2: 验证登录态
  → 检查页面是否存在用户头像/昵称元素
  → 若未登录：提示用户手动登录或提供凭证

Step 3: 选择目标板块
  → 根据 D.4 板块映射表确定板块 URL
  → 点击"发帖" / "New Topic" 按钮

Step 4: 填写帖子内容
  → 标题输入框填入生成的标题
  → 正文编辑器填入 Markdown 内容（注意富文本编辑器的粘贴兼容性）

Step 5: 发布前确认
  → 截图展示预览内容
  → 向用户确认："以上内容即将发布，确认吗？"

Step 6: 执行发布
  → 点击发布按钮
  → 等待页面跳转至帖子详情页
  → 提取并返回帖子 URL
```

### D.3 失败回退机制

| 失败场景 | 回退策略 |
|----------|---------|
| Playwright MCP 未安装/未启动 | 将帖子内容以 Markdown 文件保存至 `~/trae-drafts/`，提示用户手动发布 |
| 登录态失效 | 暂停流程，引导用户重新登录后重试 |
| 发帖按钮不可见（权限不足） | 降级为"复制到剪贴板"模式 + 手动发布指引 |
| 网络超时 | 自动重试 2 次，间隔 5 秒；仍失败则保存草稿 |
| 内容审核拦截 | 截图错误提示，记录至 riskEvents，建议修改后重试 |

**核心原则**：自动化是为了提效而非替代判断。任何不确定环节都应回退为人工确认模式。

## 最佳实践知识库

### 1. 先记录，再操作

每次在新设备上登录 TRAE 后，第一时间更新 `device-log.json`。这看似多余，但当第 N 台设备触发风控时，完整的登录时间线是你最有力的申诉材料——客服无法看到你全部的设备历史，但你自己的日志可以。

### 2. 公用电脑 = 临时标签

在任何非私人设备上登录后，务必打上 `public` 或 `temporary` 标记，并在离开时主动执行清理。不要依赖"退出登录"按钮——某些情况下服务端 session 可能不会立即释放。

### 3. 风控不是惩罚，是保护

TRAE 的风控机制本质是防止账号滥用。当你理解这一点后，应对策略就清晰了：**保持设备数量在合理范围内，及时清理不再使用的设备，避免短时间内频繁切换 IP**。大多数风控事件会在 24 小时内自动解除。

### 4. 发帖前先搜索

在生成论坛帖子之前，先用 web-search 检索社区是否有相同问题的已有帖子。重复发帖不仅浪费你自己的时间，也会稀释社区的注意力。如果找到了高度相关的帖子，考虑在该帖下方回复而不是开新帖。

### 5. 诊断报告 > 口头描述

当向客服或社区求助时，一份结构化的诊断报告（模块 B 输出）比"我登不上去了"有效得多。报告中包含的环境信息、已尝试步骤和时间线能让对方在 30 秒内理解你的问题全貌，而不是来回追问细节。

### 6. 定期审计，防患未然

建议每月执行一次完整的设备审计：列出所有设备，标记超过 14 天未活跃的设备，评估是否需要清理。这比你等到被风控拦住再慌忙查找要从容得多。可以把这个审计任务设为定期提醒。
